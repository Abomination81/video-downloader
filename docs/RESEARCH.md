# Implementation research, 2026-10-30

The architecture combines site extraction with browser observation. A single page URL or the element receiving a pointer is insufficient for multi-video pages, transparent overlays, embedded players, and MediaSource playback.

## Decisions backed by primary sources

- **Manifest V3, passive webRequest.** Observe request headers and response MIME types, including manifests with no filename extension. Keep signed URLs intact. Observing a stream does not require blocking requests. Host permission must cover both page and media hosts. [Chrome webRequest](https://developer.chrome.com/docs/extensions/reference/api/webRequest)
- **Early scripts in every permitted frame.** Use `document_start`, `all_frames`, `match_about_blank` and `match_origin_as_fallback` for dynamically embedded, blob/data/about frames. [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)
- **Closed shadow roots are accessible through Chrome's extension DOM API.** This avoids globally patching `attachShadow` in page JavaScript. [Chrome dom API](https://developer.chrome.com/docs/extensions/reference/api/dom)
- **Pointer and context-menu capture.** Capture right-button coordinates before site handlers, preserve the native default menu, and map coordinates across parent/child frame rectangles. Child identity is associated with its actual `WindowProxy`, avoiding guesses based only on equal URLs. Restore right-click by stopping site handlers at the capture stage without cancelling the browser default. This cannot reverse cancellation by an earlier handler; retain a toolbar/keyboard fallback. [MDN event propagation](https://developer.mozilla.org/en-US/docs/Web/API/Event/stopImmediatePropagation)
- **Combine site extractors and sniffed sources.** Use a known video permalink or site extractor where possible. For generic/blob players, use manifests observed in the same frame and prefer master manifests over current renditions. If several videos are equally plausible, ask the user to select. [yt-dlp](https://github.com/yt-dlp/yt-dlp), [Cat-Catch](https://github.com/xifangczy/cat-catch)
- **No extension-based guarantee of every video.** Blob handles have no direct downloadable network URL; underlying network manifests may still be accessible. WebRTC, DRM, inaccessible cached requests and Chrome restricted pages have distinct limits. [MediaSource](https://developer.mozilla.org/en-US/docs/Web/API/MediaSource), [Chrome scripting](https://developer.chrome.com/docs/extensions/reference/api/scripting)
- **Highest resolution and frame rate first.** `bv*+ba/b` has no H.264 input restriction. Compatible mode prefers original SDR H.264/AAC at equal resolution/frame rate and converts unsupported tracks when needed. Original source mode retains the former HDR/codec preference and lossless remux. [yt-dlp format selection](https://github.com/yt-dlp/yt-dlp#format-selection)
- **Install EJS and Deno.** A JavaScript runtime and the matching EJS component are needed for full current YouTube support. yt-dlp's default extra includes EJS; Deno is explicitly configured. [yt-dlp EJS](https://github.com/yt-dlp/yt-dlp/wiki/EJS)
- **Scope cookies by domain/path.** Supply real cookie objects through a cookie jar rather than attaching a global Cookie/Authorization header to arbitrary redirects. Keep cookies off disk and out of logs. [Python cookie policy](https://docs.python.org/3/library/http.cookiejar.html)
- **Native messaging broker with detached workers.** Chrome launches the broker when needed. Short broker requests and a local durable job database avoid coupling a download's lifetime to a popup or service-worker event. [Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)
- **Stable extension public key.** Unpacked users can install in different folders while retaining the native host's allowlisted extension ID. [Manifest key](https://developer.chrome.com/docs/extensions/reference/manifest/key)
- **Metadata needs several passes.** Global tags, stream tags and chapters have separate copying rules. FFmpeg stream copy can preserve private data inside codec packets. Selective SEI removal avoids stripping technical HDR/caption messages. [FFmpeg options](https://ffmpeg.org/ffmpeg.html), [bitstream filters](https://ffmpeg.org/ffmpeg-bitstream-filters.html)
- **Independent metadata inspection.** ExifTool knows many MP4/QuickTime GPS, vendor, date and user-data fields that FFprobe alone may miss. Unknown output metadata fails verification. [ExifTool QuickTime tags](https://exiftool.org/TagNames/QuickTime.html)
- **Packet remuxing without re-encoding.** PyAV exposes encoded packets, timestamps, side data and stream templates, permitting private SEI removal without altering decoded audio/video. [PyAV remux example](https://pyav.org/docs/stable/cookbook/basics.html#remuxing), [packet API](https://pyav.org/docs/stable/api/packet.html)

## Alternatives considered

Reclip and MeTube use the same yt-dlp/FFmpeg foundation and are web interfaces rather than exact-target browser detectors. Cobalt maintains selected service integrations. Cat-Catch is a useful reference for passive capture but its GPL source is not copied into this project. N_m3u8DL-RE is a potential later specialist fallback if standard manifest downloads reveal gaps. Mediabunny is a browser processing option, but a native pipeline better fits the chosen broad-coverage and independent-verification requirements. Video DownloadHelper's old CoApp is archived and its v10 architecture no longer requires it.

The extended research report is [available here](https://agent.tinyfish.ai/playground/research/share/01a18d9b-d310-72b2-bff4-70d9104f74b7). It was treated as discovery material: its broad claims about universal browser memory limits, MAIN-world requirements for DOM discovery, and Deno packaging were checked against primary sources rather than copied as implementation requirements.

## Image and browsing tools, 0.3.0

- **Lossless image cleanup through ExifTool.** Rewriting descriptive metadata avoids decoding/re-encoding the original picture. TIFF's main image directory is a special case: `-all=` deliberately leaves some fields, so descriptive IFD tags are explicitly cleared and the output is independently checked against an allowlist. [ExifTool FAQ, metadata removal](https://exiftool.org/faq.html#Q7)
- **Verify the picture separately from metadata.** ExifTool's `ImageDataHash` checks compressed image data for supported formats. Pillow additionally compares decoded animation frames, timing and loop counts, and supplements PNG/WebP/TIFF checks. Pillow is a verifier, not the output encoder. [ExifTool Extra tags](https://exiftool.org/TagNames/Extra.html), [Pillow file formats](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html)
- **Preserve orientation and color calibration.** Numerical ICC color transforms remain; source-device fields, dates and descriptive profile tags are replaced with neutral values. Unknown profile tags fail rather than silently changing color. Controlled sRGB fixtures verify identical color transforms after scrubbing. Static SVG cleanup works on XML drawing markup; active content and unsupported dependencies fail safely.
- **Two image entry points.** The extension's command prepares a verified original-format image before Chrome downloads it. Chrome's own image downloads trigger cleanup only after a new DownloadItem completes; replacement is atomic and guarded against user edits. Existing history is not scanned. [Chrome downloads events](https://developer.chrome.com/docs/extensions/reference/api/downloads)
- **Clipboard writes without reading it.** A temporary offscreen document uses the `CLIPBOARD` reason for the user-requested link copy, then closes. The extension requests `clipboardWrite`; it does not request `clipboardRead`. [Chrome offscreen API](https://developer.chrome.com/docs/extensions/reference/api/offscreen)
- **Conservative URL cleanup.** Remove a maintained set of recognizable trackers, retaining original bytes for all other query fields and fragments. Signed/session/login URLs bypass cleanup. This intentionally avoids deleting ambiguous parameters such as `ref` or mutating image/video source URLs.
- **Selection restoration at user CSS priority.** Inject selection CSS with `origin: USER` and capture common copy/selection blockers early. Form controls and editors are excluded; the setting removes injected CSS again. [Chrome scripting CSSInjection](https://developer.chrome.com/docs/extensions/reference/api/scripting#type-CSSInjection)

## Compatible MP4 default, 0.4.0

An MP4 containing AV1 video and Opus audio can be valid and playable while a service rejects it during upload. X's technical recommendations specify H.264 High Profile, YUV 4:2:0, and AAC-LC mono/stereo. Compatible mode therefore copies suitable tracks and converts other tracks with FFmpeg before the independent metadata-cleaning pipeline. Conversion preserves dimensions/frame rate (odd dimensions receive at most one padding pixel) and checks timing, frame counts, color and rotation. It never invents an audio track for a silent source. [X media recommendations](https://docs.x.com/x-api/media/quickstart/best-practices), [FFmpeg stream copy and encoding](https://ffmpeg.org/ffmpeg.html)

The profile targets codec compatibility, not platform account entitlements. X's web and API documentation publish differing duration/size guidance, so no hard-coded X account cutoff or silent trimming is applied. HDR requiring tone mapping fails explicitly in compatible mode; Original source mode preserves it. [X web uploads](https://help.x.com/en/using-x/x-videos)
